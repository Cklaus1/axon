## 0. Bottom line

- **On main, engine selection happens in one place and is consulted at three gates.** `Interp::build` (interp.rs:3461) sets `engine: vm::engine_at_build()` (interp.rs:3557). `engine_at_build` (vm/mod.rs:85-98) checks `ENGINE_OVERRIDE` (set by `set_engine`, vm/mod.rs:67-78, which only axon-wasm calls, axon-wasm/src/lib.rs:44-50), then `AXON_ENGINE`, then `Engine::DEFAULT = Vm`. Code reads the field at exactly **three** execution gates: `run_body` (vm/mod.rs:1261), `run_lambda` (vm/mod.rs:1363) and `fold_leaf` (vm/pure.rs:884). A fourth read is trace-only (vm/mod.rs:3235). Nothing outside `vm/tests.rs:238,254` writes `interp.engine` after build.
- **Below those gates, every VM execution needs a `Body`, and `vm::compile::compile` (vm/compile.rs:32) is the only thing that builds one** (the `Body {` literal at vm/compile.rs:53; `compile` is called only from `compile_entry` vm/mod.rs:1344 and `compile_lambda` vm/mod.rs:1419). This is the real choke point for defence in depth. A check in `run_body` alone (the spec's choice) misses `run_lambda` and `fold_leaf`.
- **No library caller seals a run in production.** axon-psv, axon-cortex and axon-fabric do not depend on axon-core: their `Cargo.toml` has no `axon-core` line. They spawn `axon test --seal`. The only crate that links axon-core is axon-wasm (axon-wasm/Cargo.toml:18), and it never seals. On veto, the seal state is a process-global (`resolver::SEALED_DIRS`, resolver.rs:2360-2371), and **`Interp::build` reads it** (veto interp.rs:3083-3087, `active: !dirs.is_empty()`). In-crate library tests also seal runs: they call `set_sealed_module_dirs` and then `run_test_fn_outcome` (veto taint_tests.rs:40-52; interp.rs:5718-5725). So the pin belongs in `Interp::build`, next to `seal.active`, and not in main.rs.
- **The tree engine on main is the bigger problem (Q4).** No tree path skips `call_fn_in` for a fn body. But main's AX-40..55 and R50 S2 fast paths skip *other* seal edges that veto puts elsewhere: the `plain` split inside `call_fn_in`, five raw `self.globals` reads, fn lookup through `fn_of_sym`/`callees`, and `operand()` reading BinOp operands without `eval`. Three of these re-create holes that veto already closed in C9 round 9: `TABLE[0]`, `CFG.k` and the closure-constant call. Spec §1 says only the VM skips seal edges, which is wrong.

## 3. Findings

### VmPin-1 — BLOCKER — the pin must live in `Interp::build`; "main.rs … and the axon-psv runner" misses library sealed runs and is not possible as written
- **Spec §4 Fork 1:** "the seal state set in `main.rs` (and by the axon-psv runner) is passed into the build".
- **Evidence:**
  - The axon-psv runner never links the interpreter. It spawns `axon test --seal` with `env_clear` (axon-psv/src/runner.rs:314-326), so it has nothing to pass in.
  - On veto, the seal is already decided *inside* `Interp::build` from the process-global `sealed_module_dirs()` (veto interp.rs:3083-3087).
  - Library tests seal runs without going through main.rs (veto taint_tests.rs:40-52, interp.rs:5723). Main's default engine is Vm (`Engine::DEFAULT`, vm/mod.rs:92). So with a pin in main.rs, every in-crate sealed test (T3, T4, T5 and the mutation evidence T7, which all run through the library) would execute sealed code on the VM.
- **Proposed edit:** "The pin is computed in `Interp::build` from the same input that sets `seal.active` (`resolver::sealed_module_dirs()`), in one expression. If sealed, `engine = Tree`, or refuse when a VM is requested (`AXON_ENGINE=vm` **or** `ENGINE_OVERRIDE=Vm`). Otherwise `engine = engine_at_build()`. The sealed check comes *before* the override and environment reads. main.rs adds only an early, clean refusal in `cmd_test` (before any test output); that refusal is a courtesy, not the pin." Delete "(and by the axon-psv runner)".

### VmPin-2 — BLOCKER — S1 "pins sealed runs to the tree" while main's tree has no seal edges; rollback text contradicts it
- **Spec §11:** "S1 engine pin (Fork 1) + T1, landed on main BEFORE any seal code"; "Rollback: before S7, main keeps working with the seal absent (the pin refuses sealed runs it cannot protect)."
- **Evidence:**
  - Main has no seal state at all: no `--seal` flag, no `SEALED_DIRS`, no `Seal` struct. A grep for `seal` in main.rs, resolver.rs and lib.rs on r51 found nothing.
  - S1 has to introduce a seal-state source, or T1 has nothing to test.
  - If S1 adds `--seal` and pins to the tree, then from S1 until S3 a sealed run executes on a tree that has no runtime seal edges. That is PSV-1 silently off, which is the exact hazard §1 describes.
  - The spec says sealed runs execute on the tree (§3 table, Fork 1) and also that the pin "refuses sealed runs it cannot protect" (§11). These are two different behaviours.
- **Proposed edit:**
  - S1 lands the seal-state source (`resolver::SEALED_DIRS`, `set_sealed_module_dirs`, `--seal` on `axon test`) and the pin with **refuse-all-sealed** semantics: `seal.active` → refusal, whatever the engine.
  - A single constant (e.g. `SEAL_RUNTIME_COMPLETE`), flipped only at S6 when T3-T8 are green, changes the refusal to "Tree only".
  - T1 asserts both states.
  - Also state which slice adds `--seal` to the CLI. S0 merges psv, cortex and fabric, which pass `--seal`. Until the flag exists, clap exits 2 → psv Unknown / cortex Err (fail-closed), so T6 cannot be green before that slice.

### VmPin-3 — MAJOR — the defence-in-depth check in `run_body` misses `run_lambda` and `fold_leaf`; the spec's list of VM entry points is incomplete; the true choke point is `compile()`
- **Spec §4 Fork 1:** "A second, independent check in `run_body` refuses a compiled body while `seal.active` (… every VM entry point — `run_body_vm`, `exec`, `call_fast`, `call_fast_arg`, deferred compile in S9 — passes through it)."
- **Evidence:**
  - Lambdas take the VM at `run_lambda` (vm/mod.rs:1363-1377), which never calls `run_body`.
  - `arr_fold`'s `fold_leaf` (builtins.rs:1866 → vm/pure.rs:883-958) runs compiled pure code with its own engine gate (pure.rs:884). It skips both `call_closure_owned_by` and `run_lambda`.
  - The list also leaves out `call_fast_inline`/`leaf_call` (vm/mod.rs:2746, 2802), `leaf_arm` (2714), `call_fast_local_int_slow` (2679), `fast_body`/`leaf_value`/`leaf_store`/`exec_on` (2866, 332, 2508, 1506), `call_mut_op`/`call_mut_general`/`moves_call`/`run_moves` (2910, 3206, 3026, 3114), and `compile_lambda` (1406).
  - Every one of these needs a `Body`. `Body` is built only by `compile` (vm/compile.rs:32-60; the literal is at :53), which is called only from `compile_entry` (vm/mod.rs:1344) and `compile_lambda` (vm/mod.rs:1419).
- **Proposed edit:** "Defence in depth: `vm::compile::compile` refuses while `ix.seal.active` (a Rust panic: no `Body` can exist in a sealed run). `compile` is the only constructor of `Body`, and every VM execution path needs one, so the check covers all of them by construction at zero hot-path cost. Optionally also force `FnEntry::plain = false` under seal (see VmPin-4a); `fast_call_blocker` (compile.rs:1664), `call_mut_op` (vm/mod.rs:2937) and `moves_call` (3036) refuse a non-plain entry." Replace the `run_body` sentence. Name all three gates (`run_body`, `run_lambda`, `fold_leaf`) in the drift test (VmPin-10).

### VmPin-4 — BLOCKER — tree-engine fast paths on main skip veto's seal edges and taint rule without any VM involvement (§1's "hazard" is understated)
- **Spec §1:** "R50's compiled bodies … and fast calls … skip `call_fn_in`'s dispatch, where every seal edge lives." Fork 3 and S3 talk only about Rc payloads.
- **What does *not* bypass:** every tree path that runs a fn body goes through `call_fn_in` (the `run_body` callers are interp.rs:3992 and 4159, both inside it). Every closure goes through `call_closure_owned_by` (interp.rs:4575, 4585, 4601 → 4671). `call_mut_with` goes through `call_fn_in` (eval.rs:1337). The problem is not body dispatch. It is where veto places its edges compared with main's new fast paths:

**(a) The `plain` split inside `call_fn_in`.**
- Main: `if !entry.plain || !self.refine_preds.is_empty() { return call_fn_in_general(..) } self.call_fn_common(..)` (interp.rs:3905-3908). `call_fn_common` (3982-3997) is params + `goal_met` + body + `scalar_return` and nothing else.
- Veto's per-call seal work lives in `call_fn` and `call_fn_frame`: the crossing check (veto interp.rs:3501), argument casts (:3532-3552), `with_frame` (:3983), the pin guard, taint save and restore, and the return cast (:4344).
- If the port puts these in `call_fn_in_general`, every plain fn skips them. If it adds a branch in the common path, it costs unsealed runs. The `plain` flag also gates the VM fast paths.
- **Edit:** "The seal crossing check is the first statement of `call_fn_in`, before the `plain` split. Under seal, every call takes the general path: replace `!self.refine_preds.is_empty()` with a build-time `self.general_calls = !refine_preds.is_empty() || seal.active` (one bool, so unsealed cost is unchanged)."

**(b) Global reads bypass `global_ref`/`seal_global`.**
- Veto has ONE lookup, `global_ref` (veto interp.rs:3891-3899), enforced by the drift test `every_global_read_goes_through_global_ref` (veto interp.rs:9632-9690). Its doc comment records the C9 round 9 holes: "`TABLE[0]`, `CFG.k`, `PAIR.0` read an operator global from sealed code because two fast paths skipped the edge".
- Main re-introduces exactly these as R50 S2 in-place paths, shared with the VM:
  - eval.rs:528, an existence test `self.globals.contains_key(&s)` in the Index arm
  - eval.rs:1734 `index_in_place` (`TABLE[0]`)
  - eval.rs:1758 `field_in_place` (`CFG.k`)
  - eval.rs:1248 `dispatch_named` step 4 (closure-constant call)
  - eval.rs:1872 `ident_unbound`
  - plus vm/mod.rs:2408
- **Edit:** list these six sites in S3 by name. Port `global_ref` and its drift test, extended to `interp/vm/`.

**(c) Fn lookup by name moved to `fn_of_sym` / `fn_table` / `callees`.**
- Main sites: eval.rs:1221-1245 (`callees` cache + `fn_of_sym`), eval.rs:1295 (`call_mut_entry`), eval.rs:1874 (`ident_unbound` fn-as-value, which on veto carries `seal_call` and `SEALED_FNVAL_MARK`, veto eval.rs:174-179).
- Veto's drift test `every_name_resolving_lookup_is_a_listed_sink` matches only `fns.get(`, `fns.contains_key(`, `fn_by_name(` (veto interp.rs:11281-11287). Ported verbatim, it would pass while missing every main lookup.
- **Edit:** the S3/S5 drift tests match `fn_of_sym`, `fn_of_def`, `fn_table[`, `callees`.

**(d) `operand()` reads BinOp operands without `eval`, which drops taint.**
- Main `eval_binop` → `operand()` (eval.rs:1579-1602, AX-55) copies an `Ident` or literal out of its slot and never calls `eval` on it.
- Veto applies the binding-read taint *around `eval` of the Ident expression* (veto taint.rs:1037-1048: "A read of a binding … takes its taint … Done here, around the arms"). Veto's `eval_binop` evaluates both operands through `eval_t::<T>` and reads `tl` after each (veto eval.rs:1967-1971) before `seal_width`.
- Ported onto main unchanged, `x == y` on two tainted locals produces an untainted result.
- **Edit:** "Under seal, `eval_binop` takes the evaluated path (no `operand()` fast path), either as the const-generic twin veto uses (`eval_arm::<T>`) or as a sealed-only branch outside the hot path. A drift test lists every function that reads `env.get_var` or `get_var_mut` (main: eval.rs:248, 1215, 1328, 1361, 1593, 1659, 1684, 1734, 1756; interp.rs:4821) with the rule that covers it."

**(e) `impl_method` is shared with the VM's MethodCall op.**
- `impl_method` (eval.rs:817) takes no receiver `Expr`, but veto's `seal_dispatch(receiver: &Expr, …)` needs one (veto interp.rs:3753-3759, called at veto eval.rs:715-716).
- **Edit:** keep `seal_method`/`seal_dispatch` in the tree MethodCall arm (eval.rs:474-489). Note that VM `Op::MethodCall` (vm/mod.rs:2270) skips that arm. This is irrelevant under the pin but must be listed for §12 Q1.

### VmPin-5 — MAJOR — `SEALED_*_MARK` cannot be capture-cell entries on main
- **Spec §4 Fork 3:** "the PICK bit … re-derived on the new constructors"; marks are not mentioned.
- **Evidence:**
  - Veto marks closures with NUL-prefixed `String` keys in the capture map (veto interp.rs:490-497; read at :4762).
  - Main's capture cell is a slot-ordered `RefCell<Vec<(Sym, Value)>>` (interp.rs:332-335). Slotted lambda params start at `param_base` = number of captures (sym.rs:285-288; interp.rs:4658-4660). The AX-31 lend swaps the cell into `env.vars` (interp.rs:4649). `fold_leaf` requires `cell.len() == param_base` (pure.rs:900).
  - An extra mark entry shifts every slot and breaks resolution.
- **Edit:** "Seal marks (`SEALED_CLOSURE_MARK`, `SEALED_FNVAL_MARK`, `PIN_FN_MARK`) become fields of `ClosureVal` (or of `ClosureCode` for fn values), never capture entries."

### VmPin-6 — MINOR — the refusal code exists, but not as the spec describes it
- **Spec §6:** "the existing usage/refusal code the sealed runner already uses for a malformed sealed invocation".
- **Evidence:**
  - Veto has no "malformed sealed invocation" refusal: `set_sealed_module_dirs` accepts any path (resolver.rs:2365-2371).
  - `cmd_test` exits **2** for resolve errors, check errors and type errors, which includes the seal's static refusal E0004 (veto main.rs:6199, 6207, 6225). Main's `engine_at_build` exits **2** for an invalid `AXON_ENGINE` (vm/mod.rs:93-95). clap usage errors are also 2.
  - Consumers fail closed whatever the code: psv → Unknown (runner.rs:268-276); cortex → Err when there is no summary (runner.rs:2463-2469). The psv runner binary's own "no verdict" exit is 3 (bin/axon-psv-runner.rs:7-9). That is the runner's code, not the child's.
- **Edit:** "Exit 2 (the code `axon test` uses for a resolve or type refusal, and R50 §3's invalid-`AXON_ENGINE` code). Message on stderr only. Emitted before any NDJSON line, so stdout never contains a `{"type":"summary"…}` line. T1 asserts all three."

### VmPin-7 — MAJOR — the real sealed case is `AXON_ENGINE` *unset*, plus the in-process override
- **Spec §3 / T1** focus on refusing `AXON_ENGINE=vm`.
- **Evidence:**
  - Both production sealed routes clear the environment: psv `env_clear` (runner.rs:326); fabric `with_clean_env` (submit.rs:999 → cortex runner.rs:2269-2270). The child therefore gets `Engine::DEFAULT = Vm`, and the pin must override the *default*, not just the variable.

## 4. Proposed T1 design (replaces §8 T1)

**T1a — pure truth table (unit test, no environment mutation).**
- Refactor the selection into `fn engine_for(sealed: bool, override_code: u8, env: Option<&OsStr>) -> Result<Engine, EngineRefusal>`. `engine_at_build` and `Interp::build` call it with the live values.
- The test enumerates sealed {false, true} × override {0, 1, 2} × env {None, "tree", "vm", "garbage"}, 24 rows. It also asserts that `AXON_VM_EAGER` is not an input.
- Expected:
  - Sealed rows: `Ok(Tree)` iff override ≠ 2 and env ∉ {"vm"}; `Err(Refusal)` for vm; `Err(Invalid)` for garbage. **No sealed row returns `Vm`.**
  - Unsealed rows: R50 §3 unchanged.
  - Before S6 (VmPin-2): every sealed row is `Err(SealNotPorted)`.

**T1b — library integration.**
- Under the seal test lock: `set_sealed_module_dirs([tmp])`, then a program whose sealed part has:
  - a hot loop fn (S9 hot-on-entry)
  - a fn called ≥ 3× (S9 second-entry compile)
  - a one-param int recursion (`CallFastLocalInt`, `leaf_arm`)
  - a 2-param leaf fn (`leaf_call`)
  - an `&mut [i64]` swap helper (`MovesCall`)
  - `arr_fold` with a pure 2-param lambda (`fold_leaf`)
  - `arr_map` with a lambda
- Run `run_test_fn_outcome` with override = 0 (and, in a second case, `set_engine(Vm)` → must refuse).
- Assert the outcome is `Completed`, `interp.engine == Tree`, and every `compiled` OnceCell and `LambdaBody` is empty (a `#[cfg(test)]` accessor).
- The same program unsealed under `set_engine(Vm)` must show those cells **filled**. This is the control that proves the fixture reaches every VM path.

**T1c — CLI (cli_run.rs, subprocess).**
